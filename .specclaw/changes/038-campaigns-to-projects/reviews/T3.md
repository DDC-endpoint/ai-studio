## Findings

### [NOTE] src/mcp/tools/generate.ts:~85 and src/app/api/acp/run/route.ts validateGenerateInput — Security/validation

MCP gives `projectId` no type check. ACP does (`projectId must be a string`). A non-string value reaches `prisma.project.findFirst({ where: { id: <object> ... teamId } })`. Prisma would take an object as a filter. The query stays team-scoped, so there is no leak. The effect is a Prisma validation error or a different project of the caller's own team. Fix: `typeof args.projectId === 'string'` in `generatePost`.

### [NOTE] src/app/api/drafts/[id]/route.ts:~158 — Performance

The 4 s draft poll now runs `postContext(draft)`: a project query, a kit query with prompts and logo artifacts, and a briefing query. Before, it was one kit query. FR-12 only needs the kit name and the project name. This is acceptable but is a heavier poll. Consider a name-only read if the poll shows up in load.

### [NOTE] tests/unit/postContextSites.test.ts:32 — Test teeth

Rule 1 matches `as PostContext` and `as unknown as PostContext`. It misses an alias import (`import type { PostContext as PC }` then `as PC`) and an angle-bracket cast. The brand is type-level only. `tests/helpers/postContext.ts` forges one legitimately, because the scan covers `src/` only. Teeth for src/ are adequate for the usual case. Optionally widen the regex to any `as <alias>` of an imported `PostContext`.

### [NOTE] src/components/brief/useBriefWizard.ts selectProject — behaviour

Choosing a project overwrites a kit the user already picked on step 1. The step order makes this unlikely (project is step 0), and the user can change the kit again. No action needed.
