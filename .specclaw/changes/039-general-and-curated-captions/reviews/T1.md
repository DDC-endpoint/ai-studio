## Findings

### [NOTE] src/lib/captions/store.ts:~405 (saveCaptionEdit) — Correctness (behaviour change)

**Problem:** The edit is now read then `updateMany` guarded by `updatedAt: row.updatedAt`. A write that lands between the read and the update (a settle or another edit) makes the edit return false, and `src/app/api/drafts/[id]/route.ts:339` answers `beingGenerated()`. Before, the single `updateMany` (status not PENDING) always won. The window is milliseconds and the outcome is a retryable refusal, not data loss, but T1 was "no behaviour change".
**Fix:** None required. State it in the T3 notes, or drop the `updatedAt` guard until T3 needs it for the return union.

### [NOTE] src/lib/agent/prompts/caption.ts:24 — Behaviour change (token budget)

**Problem:** `captionMaxTokens(targets)` replaces the flat 8192. For headline plus Instagram and LinkedIn it is 512 + 100 + 2200 + 3000 = 5812, and a regenerate of one target is far smaller. The design (line 360) specifies this formula, so it is compliant, but it is a real reduction (about 29% for the full call) for non-Latin scripts (Sinhala can exceed one token per character), where a truncated JSON reply would fail the whole write.
**Fix:** Keep as designed, or add headroom in T2 and note it. Worth a Sinhala mock or real-size check before T2 ships the single general call.

### [NOTE] prisma/rollback/039-general-and-curated-captions.down.sql:19 — Correctness

**Problem:** The information_schema lookup `WHERE table_name = 'BrandKit'` is not schema-qualified, so a same-named table in another schema could trigger the EXECUTE against the wrong table. Negligible in this deployment.
**Fix:** Add `AND table_schema = current_schema()`.
